# called-it: the contract

You are hosting the `/called-it` skill. You do the reading, searching and judging; the script at
`$SKILL_DIR/scripts/called_it.py` does everything that must be deterministic and replayable:
fetching, caching, asking the grader, scoring, rendering. `$SKILL_DIR` is the directory of this
file. Run the script from the repo root (the directory that holds `runs/`), or from any folder
you want the `runs/` folder created in.

```bash
CALLED_IT="python3 $SKILL_DIR/scripts/called_it.py"
```

## Eight laws

1. **Rubrics before evidence.** Every claim gets its three bars written and checked before a single
   search for evidence runs. If a bar is edited after evidence is in, record the edit in the rubric's
   `revisions` list with the reason. Writing the bar after seeing the result is how self-grading goes wrong.
2. **Never grade from memory.** You may know what happened in the target year. It does not count. A
   bar is met only on rows in `evidence.jsonl` that were fetched, dated and quoted. If you cannot
   find evidence for something you believe happened, the verdict is `unresolved`, and that is correct.
3. **Never guess at an unreadable source.** If `fetch` reports a source unreadable (paywall, login,
   402, 403, blocked), tell the user the exact URL and ask them to paste the text, log in, or skip
   it. Never grade a paywalled piece from its preview or from your recollection of it.
4. **Quotes are verbatim.** `quote` fields hold the author's words as fetched, with nothing changed
   but whitespace. Paraphrase goes in `context`, labeled as yours.
5. **The critic floor.** The lenient bar is lenient about the claim's scope, never about the evidence.
   Tier 5 (social chatter) is never sufficient on its own. An author claiming their own hit is tier 4
   and weak; an author admitting a miss is tier 4 and strong.
6. **Split, do not argue.** When one prediction hides two definitions (did a car fly, or do cars now
   fly between cities), make two claims with `split_of` set to the parent, each with its own bars.
7. **Whose claims.** Grade the subject's own words. A guest's predictions on the subject's podcast are
   recorded with `author` set to the guest and `attribution: "guest"`, and the report shows them apart.
8. **The footer passes through.** The report's last block (tool version, grader model, thresholds,
   counts, spend) is generated by the script. Include it verbatim. It is how a reader knows what the
   run had.

Style for anything you write into the report synthesis: no em dashes or en dashes (use a comma, a
period or ` - `), no invented section headers beyond the template, inline markdown links for every
citation, and no `Sources:` block at the end (the evidence table is the sources).

## Stage 0: intake

Collect from the user: the subject (person, company or publication), the target year, at least one
canonical URL where the predictions were made, and optionally a website, X handles, attachments
(files the user drops into `runs/<run>/attachments/`), and a different window. Defaults for target
year Y: season window Oct 1 (Y-1) to Jan 31 (Y); evidence window Jan 1 (Y) to today.

```bash
$CALLED_IT init <run> --subject "Every" --kind company --website https://every.to --year 2026 \
  --canonical https://every.to/context-window/every-s-2026-predictions --x-handles every,danshipper \
  --domains "AI,software,media,work"
```

`init` prints which grader is available. With `TYPESAFE_API_KEY` set, Jev (TypeSafe's System One model)
answers every typed question. Without it, **you** answer them (see "Answering pending questions").

## Stage 1: discover sources

Find every place the subject published predictions for the target year inside the season window.
Start from the canonical URL, then: the website's archive for those months, X search (the script
can do it with `X_BEARER_TOKEN`: `$CALLED_IT x-search <run> <handle> --count-only` first, then without
`--count-only` if the count is reasonable; posts cost money to read, so say the estimate), podcast
feeds and YouTube (captions are fetched with yt-dlp if installed), newsletters, decks, PDFs. Also
find the prior year's list if there is one, and any self-grading the subject published; both are
context, and the self-grade is tier 4 evidence later.

Write one row per source to `runs/<run>/sources.jsonl`:

```json
{"id": "s1", "url": "https://every.to/context-window/every-s-2026-predictions", "title": "Every's 2026 Predictions",
 "author": "Every staff", "date": "2025-12-23", "format": "newsletter", "access": "free",
 "role": "canonical", "note": "11 predictions, several are editor paraphrases of team members"}
```

`format` is one of essay, newsletter, thread, podcast, transcript, video, pdf, deck, article, page,
other. `access` is free, paywalled, login or unreadable. `role` is canonical, additional, prior_year,
self_grade or context. For a YouTube episode use `"url": "youtube:<video id>"`. For an X thread,
hydrate it first so the claims are the posted text, not a mirror's paraphrase:

```bash
$CALLED_IT x-thread <run> <root post id> <username>     # needs X_BEARER_TOKEN; stores the thread as text
$CALLED_IT fetch <run>                                  # fetches every source into cache/pages
$CALLED_IT text <run> s1                                # prints a source's extracted text for you to read
```

`fetch` lists anything unreadable. Apply law 3. Text the user supplies goes in with
`$CALLED_IT add-text <run> <id> <file>`; a caption file with `add-captions`.

## Stage 2: extract claims

Read every readable source in full (`text`). Write one row per discrete prediction to
`runs/<run>/claims.jsonl`:

```json
{"id": "c1", "source_id": "s1", "quote": "A mass-market robotic pet succeeds by the end of 2026.",
 "author": "Willie Williams", "attribution": "subject", "date": "2025-12-23",
 "context": "Listed as the team's wildcard prediction.", "domain": "hardware", "horizon": "2026-12-31"}
```

Rules: one checkable outcome per row (split compound sentences); keep the author's numbers and dates;
`horizon` is the date by which the claim says it happens (default Dec 31 of the target year);
`attribution` is subject or guest; `split_of` names a parent claim when law 6 applies; set
`"pinned": true` to force a claim into the selected set regardless of rank (say why in `context`).

Then let the grader score and rank them, and screen the sources for predictions you missed:

```bash
$CALLED_IT classify <run>     # is_prediction, specificity, binary vs spectrum, boldness; selects the top N
$CALLED_IT screen <run>       # passages that read as predictions but match no claim -> screen.jsonl
```

Read `screen.jsonl`. Add real misses to `claims.jsonl` and rerun `classify`. Claims the grader scores
`is_prediction < 0.5` are listed; either sharpen the quote (you probably cut the forward-looking part)
or accept that it is not a prediction and leave it unselected.

## Stage 3: write the three bars (then stop for the human)

For every selected claim, write `runs/<run>/rubrics.jsonl`:

```json
{"claim_id": "c1", "kind": "binary",
 "bars": {
   "strict":   {"criterion": "A mass-market robotic pet is a clear commercial success in 2026: a consumer robotic pet launched in 2026 and sold at least 100,000 units by year end.",
                "measure": "Unit sales per the maker or a major outlet; a Sony Aibo refresh does not count as a new launch."},
   "standard": {"criterion": "A consumer robotic pet launched or went on general sale in 2026 and reached mainstream retail or widely reported strong sales.",
                "measure": "Major-outlet reporting of retail distribution or sales; maker claims alone are tier 4."},
   "lenient":  {"criterion": "At least one consumer robotic pet launched in 2026 and was widely covered as a commercial success, even without unit numbers.",
                "measure": "Two or more major outlets describing it as a hit."}},
 "notes": "'Succeeds' is undefined in the source; the bars make three readings explicit.",
 "revisions": []}
```

Two fields per bar. **`criterion` says what counts, in the author's own terms**: a plain sentence a
reader of the prediction would recognise as a reading of it, with any numbers the author gave kept
and any number you add stated as yours. **`measure` says how we look**: the series, index, source,
date rule or proxy, and whether the result is provisional before the horizon. Keep them apart. The
critic check (next step) judges the `criterion` alone; the grader sees both fields. The check is a
review aid, not a gate: its acceptance moves with wording in ways that are not monotonic (in testing,
a bar that named an index scored higher than the same bar in plain words), so read each flag, fix a
bar when the flag is right, explain it in `notes` when it is not, and never iterate wording just to
raise the number. One more rule from the first runs: **never write a bar as a universal negative**
("no reading in 2026 was at or below X"), because proving it needs complete data and the grader will
rightly return unresolved; write the positive form over the latest reading or the year's extreme
("the lowest 2026 reading was above X, per the full series"). Strict is what a hostile critic requires;
standard is what a fair reader accepts; lenient is the weakest reading a critic would still concede.
For a binary claim with nothing to be lenient about, the three may be identical; say so in `notes`.
Then:

```bash
$CALLED_IT check-rubrics <run>   # grader: would a skeptical critic accept each bar as fair? is it checkable?
```

Fix every FLAG or explain it in `notes`. **Now show the user the rubric sheet** (claims with their
three bars) and ask them to approve or edit before any evidence is gathered. This is the one
checkpoint that needs a human. If the user is away, say that you are proceeding with the bars as
written and that they can edit and `replay` later.

## Stage 4: gather evidence

Only now search the evidence window. For each selected claim and bar, look for evidence that the
criterion was met and evidence that it was not: web search with the window in the query, official
sources (filings, release notes, announcements), reputable reporting, resolved prediction markets
(`$CALLED_IT markets <run> "<question>"` checks Polymarket and Kalshi), the subject's own later posts
(mid-year check-ins, "grading my predictions", retractions), and the user's attachments. If the
`last30days` skill is installed, `--days N` covering the window is a good deep pass per claim.

Write one row per item to `runs/<run>/evidence.jsonl`:

```json
{"id": "e1", "claim_id": "c1", "bars": ["standard", "lenient"], "url": "https://...", "date": "2026-06-11",
 "source": "The Verge", "tier": 2, "direction": "supports", "quote": "the exact sentence that bears on the criterion",
 "found_by": "websearch"}
```

Tiers: 1 primary (announcement, filing, shipped product, on-chain or price data, official statistics);
2 reputable reporting; 3 resolved market; 4 the author's own later statement; 5 social chatter.
`direction` is supports, contradicts or neutral. `bars` lists the bars the item bears on (omit for all).
`found_by` is websearch, fetch, x, polymarket, kalshi, attachment, author or user. Prefer two
independent items over one. Record contradicting evidence as diligently as supporting evidence; a
grade with only supporting rows is a grade nobody looked hard at.

## Stage 5: grade

```bash
$CALLED_IT grade <run>
```

For every (claim, bar) with evidence, the grader answers three questions over the exact evidence
rows: is the criterion met, does the evidence show it was not met, and how strong is the best
evidence. The script turns those into `met`, `not_met` or `unresolved` with the thresholds in
`run.json`, and prints hit rates per bar and the generosity gap (lenient minus strict). Pairs with no
evidence are `unresolved: no evidence gathered`; go back to stage 4 for any that matter.

## Stage 6: report

```bash
$CALLED_IT report <run>
```

Writes `report.md`, `report.html` and `data.json`. Show the user `report.md` with a short synthesis
above it: the headline (hit rates at the three bars), the two or three claims where the bars disagree
most, anything unresolved that a human could settle, and a line on what the run had (grader, sources
unreadable, X spend). Then the report verbatim, footer included (law 8).

Anyone can later run `$CALLED_IT replay <run>` with no key and no network and get the same
scorecard, or `grade` again live and diff the probabilities.

Two drafts follow the report. `$CALLED_IT post <run>` writes `post.md`, the self-review thread the
subject could publish. `$CALLED_IT share <run>` writes `share.json` and `share.md`: the quote-post
for sharing the scorecard (one line of numbers under 160 characters, the author's original post to
quote when one is among the canonical sources, the 1200x630 card, the scorecard page link and a
one-click X intent URL). Offer both to the user; never post anything yourself.

## Answering pending questions (no TYPESAFE_API_KEY)

When no key is set, `classify`, `screen`, `check-rubrics` and `grade` write each unanswered question
to `runs/<run>/cache/jev/pending/<hash>.json` and tell you how many are waiting. Answer each one in
the same typed shape the API would return, then rerun the command; it reads the cache and continues.

For each pending file, read `state` and `questions`, then write `cache/jev/answers/<hash>.json`:

```json
{"hash": "<same hash>", "requested_model": "<from the pending file>", "answered_model": "model-fallback:<your model name>",
 "grader": "model-fallback", "state": <copy>, "questions": <copy>,
 "answers": {
   "met": {"type": "noul", "noul": 0.82},
   "contradicted": {"type": "noul", "noul": 0.05},
   "strength": {"type": "score", "score": 1.7, "confidence": 0.7, "probabilities": {"0": 0.0, "1": 0.3, "2": 0.7},
                "legend": {"0": "...", "1": "...", "2": "..."}}
 }, "at": "<ISO timestamp>"}
```

Rules for your answers: a noul is your probability that the statement is true given only `state`
(not what you know from elsewhere); a score's `probabilities` sum to 1 over the levels in the question
and `score` is their weighted mean; a choice has `choice`, `confidence` and `probabilities`. Answer
each question independently. Do not look at other pending questions to keep yourself consistent;
answer the one in front of you. Delete nothing from `pending/`; the script does that when it reads
an answer.

## Costs and keys

Keys are read from the environment only (`TYPESAFE_API_KEY`, `X_BEARER_TOKEN`); never write them
into a run folder. Jev calls cost fractions of a cent per question. X reads bill per post; the script
prints an estimate before any search and logs every read to `cache/x/xapi-ledger.jsonl`, which the
report footer sums. Say the estimate to the user before a search over a few hundred posts.
